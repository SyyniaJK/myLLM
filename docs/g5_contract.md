# G5：研究问题诊断契约

本轮执行用户提供讨论中的 G5-1 至 G5-6。目的为筛选问题，不开发新优化算法、不重新训练神经网络、不改写 G1–G4 的结果。配置在 `configs/g5.json`，先固定配置再运行。参数网格是模型敏感性诊断，未声称由真实无线网络或 GPU 测量标定。

## G5-1 / G5-2：能耗依据与可控制项

核对相位功率、无线功率、有效载荷、速率公式及计算模型的单位和来源。15/60/45 W、8 bits/token、96.5 TFLOPS 等仍属模型假设。恒定相位功率 × FLOPs 时间不是经过校准的 GPU 能耗预测器。没有 GPU 测量时，不将模型恒等式检验表述为物理校准。

原论文速率按总噪声功率和线性带宽比例计算；本轮保持该近似，不切换为分配带宽相关噪声谱密度模型。无线载荷没有包含协议/文本序列化开销。参考 [Zeus 测量定义](https://ml.energy/zeus/measure/) 与 [TokenPowerBench](https://github.com/chenxuniu/TokenPowerBench) 明确模型积分和硬件测量的区别；没有运行这些硬件工具。

直接分解已有 G4 的 1800 条原始记录：固定空闲基线、窗口 GPU 增量和射频能耗。可控制项占比仅是“假定消除全部变量项”的代数上限，不是保持服务量时可实现的节能幅度。当前节点常开，调度不能消除固定基线。

## G5-3：无线 × 提供负载

额外上下行链路衰减为 0/20/40 dB，mean_think 为 8/2/0.5 秒，固定时隙请求提供概率为 1−exp(−1/mean_think)。负载轴是提供请求强度，实际 GPU 利用率另测。40 dB 为压力诊断，不将其影响外推为常态网络现象。

每个负载的 5 个新场景保存原始信道及请求，衰减通过乘以 10^(−dB/10) 生成。相同负载的衰减/方法/资源分配比较严格共享外生请求，负载之间不声称请求数相同。六种 G4 方法 × 三个策略 seed × 两个上行分配器，200 秒固定窗口，共 1620 次评估。

两个分配器只改变上行：TP P2 与等分上行；下行均保持 TP P3。两种 PPO 复用 nominal/default 的最终策略，仅检查输入/输出维度相同；这是冻结策略的分布迁移诊断，不声称已在新条件训练。

保留窗口 GPU 增量、尾部 GPU 增量、所有已接纳批次完整 GPU 增量，以及 padding 相对独立请求的额外工作。射频记账置零为 `E_without_RF=E_total−E_up−E_down`，速率中的实际发射功率和所有时延保持不变；它不是零发射功率仍通信的物理系统。

完整 GPU 增量按各批次模型的 prefill/decode 时长乘相位增量功率计算，避免用“大绝对时间相减”的浮点误差解释能耗变化；另存 `gpu_increment_full_ledger_j` 对照区间积分。主窗口能耗仍直接使用原 G4 ledger，未改写其物理实现。

单批次控制另外验证：相同请求和放置下，上行分配只能改变开始时间/SLO；在当前相位功率模型中，完整 GPU 增量不随上传等待改变。窗口内 GPU 能耗的下降可能只是工作移到窗口外，不能直接解释为节能。

## G5-4：SLO × 批次组成

控制快照使用 10 用户/3 节点模型，其中 6 个用户各有一个请求，统一在 0.5 秒到达：三个 (input=128, output=128)，三个 (512,1024)。固定同一组请求、信道和两个工作节点，每节点三个请求，第三节点保持相同基线。

`grouped` 将两类分别放到两个节点；`mixed` 每节点混合两类。扫描统一 SLO=1/2/4 秒、0/40 dB、两个上行分配器和五个场景，共 120 个控制快照。它是固定放置的机制实验，不是新调度算法。12 秒观察窗覆盖所有可能按时成功的响应；尾部仍另记。

## G5-5：长度估计误差

使用高提供负载、固定相同请求，分别测试 16/24 GB 显存和六种长度输入；仅替换 cap 贪心的内部长度估计，不改变环境中的真实请求、输出或物理执行。

- `cap`、`conditional_mean`、`half_cap` 使用 cap、生成分布均值 0.75×cap、0.5×cap，均为因果可见的诊断代理，不是训练的预测器。
- `oracle`、`oracle_half`、`oracle_over` 使用真实输出、0.5×真实输出、1.25×真实输出，明确为含未来信息的离线控制，不能作为可部署方法。

共 60 次完整评估。报告估计误差、OOM、拒绝、服务和能耗。OOM 沿用现有“上传后解析检测，未执行 GPU”语义；因此不据此声称实测 GPU OOM 恢复代价。

## G5-6：小规模条件精确对照

使用上述六请求快照。枚举每个请求拒绝或放至三个节点的全部 4^6=4096 个放置，每个节点子集通过同一个 EdgeEnv 执行计算，缓存只利用当前单批次/节点独立可加的结构。对 SLO、衰减、场景共 30 个快照建立“相同成功数下最小完整变量能耗”的前沿。

`oracle_exact` 用真实长度评价全部候选，最大化按时成功数，再最小化完整 GPU 增量与射频能耗；属于知晓未来长度的理想参照。`cap_exact` 只用 cap 构建候选成本并选择放置，选定后在真实长度模型评价。六种基线使用 users_10 的原策略/规则，三重复，共 540 次基线快照；两个精确计划每快照各一次，共 60 次。

这里的“精确”仅针对给定请求、信道、模型和固定 TP P2/P3 分配规则的单次放置枚举，不是完整时域策略或任意连续无线分配的全局最优。变量能耗在批次完成后全部计费，不利用窗口截断；固定基线是所有计划共享的常数。与主扫描的窗口 J/Goodput 分开解释。服务差距与同服务数能耗差距分别报告。

## 统计、重放与图表
